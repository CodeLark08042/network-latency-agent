# 校园网延迟调查

## 何时使用

使用：用户报告某条链路或某段路径变慢、RTT 升高、吞吐下降、丢包，需要定位延迟来源。

不要使用：DNS 解析失败、应用层响应慢、无线空口信号差。这三类问题的判据与本 Skill 不同，应当直接说明超出范围，不要套用延迟分解。

## 调查顺序（按此顺序执行，不要跳步）

1. `list_network` 取拓扑，确认待查链路的上下游。
2. `get_link_metrics` 查可疑链路，并**至少再查一条对照链路**。只看一条链路不能下结论。
3. `analyze_delay_components` 分解四类时延，看哪一类占主导。
4. 仅当第 3 步显示排队时延显著（占总量 30% 以上）时，才调用 `calculate_queue_delay` 复算；否则不要调用，省下预算。
5. 汇总证据写结论。

工具预算 5 轮，用完立即收尾。

## 四条硬性规则（违反任一条即视为调查失败）

1. **数据缺失必须明说。** 某条链路的指标为 null 或缺失时，写"缺少 X，无法据此判断"。禁止用"其他链路指标正常"来掩盖没查过的部位，也不许估算缺失值。
2. **置信度与数据完整度绑定。** 只要有任一关键指标（利用率、RTT、丢包、队列）缺失，置信度不得超过 50%；并且结论一节要改写成"证据不足，候选原因排序如下（不给置信度断言）"，不得写成"最可能的原因是 X，置信度 N%"。数据完整时才可给出单一结论。
3. **理论值与实测值相差超过 10 倍必须解释。** 解释不了就写"现有数据不足以解释该差异，倾向于还有其他因素"；不要反过来把理论值说成与实测"高度吻合"。
4. **ρ ≥ 1 时禁止给出排队时延数值。** M/M/1 在 ρ ≥ 1 时前提不成立，只能报告"系统过载、队列将无限增长"。

工具参数必须传纯数值，不要把算式当参数（例如不要传 `"1000 / (700 * 8)"`，传 `0.178`）。

## 判读表

| 利用率 | 丢包 | 队列深度 | 更可能的结论 |
| --- | --- | --- | --- |
| > 80% | 有 | 大（数百） | 链路拥塞，排队时延占主导 |
| 正常或偏低 | 高 | 可能大 | 硬件故障或链路误码，丢包引发重传 |
| 各段都不高 | 低 | 小 | 路径变长（路由变更），检查传播时延与路径 |
| 全部为 null 或缺失 | — | — | 数据不足，无法确定 |

判断依据必须写清用了哪几列数据；只有一行数据不足以支撑结论。

## 输出要求

按以下顺序写：

1. 问题概述；
2. **证据表**：字段 / 数值 / 判读（例如 `utilization=0.92 → 超过 0.7 警戒线`）；
3. 假设逐条列支持证据与反驳证据，被自己找到的证据反驳的假设要明确降级；
4. 结论 + 置信度（受规则 2 约束）；
5. 建议：可操作、可验证。

## 必须承认证据不足的情形

- 关键链路指标缺失或为 null；
- 理论时延与实测相差一个数量级以上且无法解释；
- 两个假设各有部分证据，无法区分；
- 只有一个时间点的快照，无法判断是持续问题还是瞬时抖动。

以上情形要说"证据不足"，并指出还缺哪些数据。说不知道是合格答案，编一个高置信度结论是错误答案。
